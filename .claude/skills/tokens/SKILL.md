# Tokens: export and rebuild

Tokens flow one way: **Figma → `tokens/` → `build/` → components.** Every arrow is a machine step. A person or an agent changes tokens in exactly one place, which is Figma.

## The one rule

**A missing token is reported and fixed in the design tool. It is never added to a generated file.** If a component needs a token that does not exist, the Designer creates or binds the variable in Figma, re-exports, and the build regenerates. Typing a token into `tokens/*.json` or `build/css/tokens.css` makes the code disagree with the design, and the next export silently deletes it.

## What is generated, and by what

| Path | Written by | Hand-edit? |
|---|---|---|
| `tokens/*.tokens.json`, `tokens/manifest.json` | The Figma export plugin | **Never.** The plugin owns these files. A hand edit is overwritten by the next export |
| `build/css/tokens.css` | `npm run build:tokens` (`build-tokens.js`) | **Never** |
| `build/ios/Tokens*.swift` | `npm run build:tokens` | **Never** |
| `build/android/tokens*.xml` | `npm run build:tokens` | **Never** |
| `build-tokens.js` | A human, by reviewed change | Yes, but only to add a *rule* (see below) |

`build/` is deleted and rewritten on every build. Every generated file says so in its header: `Do not edit directly, this file was auto-generated by build-tokens.js.`

If the export has the wrong **shape**, the fix is a rule in `build-tokens.js`, never an edit to the export. Examples of wrong shapes are a duration exported as pixels, a z-index with a unit, or an opacity of `40` instead of `0.4`. The preprocessor already holds those rules, and each one names the shape it repairs. A wrong **value**, such as a colour that is simply the wrong colour, is a design change, so it is fixed in Figma.

## Export and rebuild

1. **The Designer exports** from Figma with the token plugin into `tokens/`, replacing every file, `manifest.json` included.
2. **token-runner takes over** when the Designer says they have re-exported (`.claude/agents/token-runner.md`). It branches `tokens/sync-<description>`, runs `npm run build:tokens`, summarises the diff in designer language, and opens a pull request. It stops for review if more than 20 tokens changed.
3. **Verify the rebuild** (below) before the pull request is merged.

Nobody merges token changes to `main` except through that pull request.

## Modes

The manifest defines **5 collections and 11 modes**. The first mode listed for each collection is its default, and it goes into `:root`. Every other mode becomes an override block that redefines only the tokens whose resolved value differs from the default. Typography and effect **styles** have no modes.

| Collection | Default mode | Other modes | CSS selector | What varies by mode |
|---|---|---|---|---|
| core | light-mode | none | n/a | Nothing. The colour palettes, spacing scale, radii and font sizes are single-mode |
| semantic | light | dark (**123** tokens) | `[data-semantic="dark"]` | Every semantic colour (`--color-bg-*` 38, `--color-border-*` 27, `--color-status-*` 18, `--color-text-*` 16, `--color-icon-*` 14) and the elevation shadows |
| typography | english | burmese (**78**) | `[data-typography="burmese"]` | The font family (Manrope → Noto Sans Myanmar), line heights, letter spacing, and every type style built from them (`--h*`, `--body-*`, `--caption-*`, `--tagline-*`) |
| layout | compact | medium (**6**), expanded (**6**) | `[data-layout="medium"]`, `[data-layout="expanded"]` | `--padding-container`, `--padding-card`, `--margin-page`, `--gap-section`, `--gap-gutter`, `--gap-card` |
| density | mobile | web (**5**), back-office (**7**) | `[data-density="web"]`, `[data-density="back-office"]` | `--density-touchtarget`, `--density-rowheight`, `--size-control-sm/md/lg`, plus `--density-controlpaddingx/y` in back-office |

`:root` holds **458** variables. Native outputs follow the same split: `Tokens.swift` and `tokens.xml` for the defaults, plus one file per override mode (`Tokens<Collection><Mode>.swift`, `tokens_<collection>_<mode>.xml`).

These counts describe the export of 2026-10-16. They change whenever the design does. Re-derive them rather than trusting this table:

```bash
awk '/^(:root|\[data-)/{s=$1" "$2} /^\s*--/{c[s]++} END{for(k in c) print c[k], k}' build/css/tokens.css
```

Two consequences for anyone using tokens:
- **A token that varies by mode must be used through its variable,** never resolved to a value. `--color-bg-base` is white in light mode and something else under `[data-semantic="dark"]`. A component that hard-codes the light value is wrong in dark mode.
- **Testing one mode tests one mode.** A component that passes in English has not been tested in Burmese, whose different font and line heights change every text measurement.

## A real token gap, or a naming mistake?

When a value seems to have no token, find out which of these it is before reporting anything. They have different owners.

The export flattens each Figma variable's path into one lowercase, hyphenated key: `color-bg-brandgreen-idle`. The CSS name is `--` plus that key.

1. **Is the property bound in Figma at all?** Check `get_design_context` or `get_variable_defs` on the node.
   - **No variable is bound:** this is a **design gap**. The Designer must bind one. Report it, and do not pick a token.
2. **A variable is bound. Does its flattened name exist in the export?** Search for the exact key:
   ```bash
   grep -l '"color-bg-brandgreen-idle"' tokens/*.json
   ```
   - **Found:** there is no gap. The code used the wrong name. That is a **naming mistake in the code**, fixed by whoever wrote the code.
3. **Not found by exact name. Is there a near-miss?** Compare with separators and case ignored:
   ```bash
   node -e 'const k=process.argv[1].toLowerCase().replace(/[^a-z0-9]/g,"");for(const f of require("fs").readdirSync("tokens"))if(f.endsWith(".json")&&f!=="manifest.json")for(const n of Object.keys(require("./tokens/"+f)))if(n.replace(/[^a-z0-9]/g,"").includes(k))console.log(f,n)' "color/bg/brandGreen/idle"
   ```
   - **A near-miss exists**, such as `surfacePrimary` against `surfaceprimary`, or a different group path: this is a **naming mismatch**. The variable exists, but under a different name from the one used. If the code used the wrong spelling, fix the code. If Figma and the export disagree, the export is stale or was renamed: report it to the Designer to re-export or rename.
4. **No near-miss either. Is the variable in Figma but missing from the export?** If `get_variable_defs` shows the variable but `tokens/` lacks it, the **export is stale or incomplete**, for example a collection that wasn't exported. Report it to the Designer to re-export.
5. **No such variable anywhere:** this is a **real token gap**. The design needs a token that does not exist. Report it to the Designer, who creates it in Figma. Then re-export and rebuild.

Also rule out the base-layer mistake: a value that matches a **base** token (`--color-forest-green-600`) is not a gap when a semantic token (`--color-bg-brandgreen-idle`) points at it. Use the semantic one. A token that another token points at through `var(--…)` is base, and components do not use it.

In every case except a naming mistake in the code, **nothing is added to `tokens/` or `build/`.**

## Verify the rebuild, do not assume it

A build that exits 0 can still drop a mode, print `NaN`, or leave a reference dangling. Prove it is right.

1. **Run the build and read its output.** `npm run build:tokens` must exit 0 and print a `✔` for each file it writes. The build itself refuses two errors: a mode block that declares a name `:root` lacks, and a `var()` with no definition.
2. **Run the verifier:**
   ```bash
   node scripts/verify-tokens.mjs
   ```
   It must end `RESULT: PASS`. It checks that:
   - the manifest and `tokens/` list the same files;
   - every generated file carries the generated header;
   - every source token reached `:root`, and every `:root` name came from a source token, so nothing was hand-added;
   - there is exactly one CSS block per non-default mode in the manifest, and no block for a mode that does not exist;
   - mode blocks override only `:root` names, and every `var()` resolves;
   - no `[object Object]`, `NaN` or `undefined` appears in any output;
   - a native file exists for the defaults and for every mode block, on both platforms.
3. **Prove the build is repeatable.** Run `npm run build:tokens` a second time. `git status --porcelain build` must show nothing new since the first run. A build that changes its own output on a re-run is not reproducible.
4. **Read the diff.** `git diff --stat tokens build`, then `git diff tokens`. Every change in `build/` must be explained by a change in `tokens/` or in `build-tokens.js`. A change in `build/` with no cause upstream means someone edited it by hand, or the build is not deterministic.
5. **Check the mode table still holds.** Re-run the count command above. A collection whose override count dropped to 0, or a new mode that appeared, is a design change to name in the pull request summary.

## Never

- **Never add, edit or delete a token in `tokens/` or `build/`.** Fix it in Figma and re-export.
- **Never add a missing token to the generated CSS** "for now". It disagrees with the design, and the next build deletes it.
- **Never fix a wrong value in `build-tokens.js`.** Rules there repair shapes, not design decisions.
- **Never resolve a mode-varying token to its default value** in a component.
- **Never call a value a gap before running the gap check.** Naming mistakes and stale exports look like gaps.
- **Never use a base token** because no semantic token "seems" to fit. Report it.
- **Never trust a build because it exited 0.** Run the verifier, rebuild twice, and read the diff.
- **Never merge token changes to `main`** except through token-runner's pull request.
